# Migrate a client from API 1.0 to API 1.1

This guide is for mod authors who **recompile their client DLL with the 1.1
headers**. The menu-building API remains familiar, but discovery, language
lookup, and registration now begin with an explicit `erui::Connection`.

Migrating is a choice, not a requirement. A mod may intentionally remain on
the 1.0 SDK when it does not need 1.1 features. Every 1.x host continues to
expose the frozen API 1.0 function-table prefix, whether the client was built
before that host release or deliberately compiled from the 1.0 SDK later. Such
clients keep their original 1.0 behavior and cannot access features introduced
in API 1.1. A future 2.x host supports API 1.x only when that release explicitly
documents the retained contracts.

## Release version and API version are different

Three independent versions may appear in a mod project:

| Version | Example | What it controls |
|---|---|---|
| ERNativeUI release/package version | `1.1.0` | The downloadable SDK/host release and the version checked by CMake. |
| ERNativeUI binary API version | `1.1` | The C function-table layout negotiated at runtime with `ERUI_GetApi`. |
| Your mod's version | for example `2.4.0` | Your own release lifecycle; it does not need to match ERNativeUI. |

`find_package(ERNativeUI 1.1.0 CONFIG REQUIRED)` checks the installed **package
version** during configuration. `erui::connect()` requests **API 1.1** from the
DLL at runtime. Passing one check does not replace the other.

In the C header, API 1.1 is the encoded value
`ERUI_API_VERSION_1_1`, not the semantic release string `1.1.0`. A future
ERNativeUI `1.1.x` maintenance release can keep exposing exactly the same API
1.1 ABI.

## The required C++ source change

### Before: API 1.0

The 1.0 wrapper hid host discovery inside the free `erui::register_menu`
function. Its timeout lived in `ProviderOptions`:

```cpp
erui::ProviderOptions options{};
options.provider_id = "my-mod";
options.display_name = L"My Mod";
options.owner_module = g_module;
options.connect_timeout = std::chrono::milliseconds{5000};

const auto result = erui::register_menu(
    options,
    [](erui::Menu& menu) {
        menu.root().add_toggle(
            L"Enabled", L"Enable this mod.", 1, &enabled_changed);
    });
```

### After: API 1.1

Connect once, handle that result, and register through the returned
`Connection`:

```cpp
const auto connection =
    erui::connect(std::chrono::milliseconds{5000});
if (!connection) {
    log_error(connection.error().message());
    return; // Only the optional ERNativeUI integration is disabled.
}

erui::ProviderOptions options{};
options.provider_id = "my-mod";
options.display_name = L"My Mod";
options.owner_module = g_module;

const auto result = connection.value().register_menu(
    options,
    [](erui::Menu& menu) {
        menu.root().add_toggle(
            L"Enabled", L"Enable this mod.", 1, &enabled_changed);
    });

if (!result) {
    log_error(result.error().message());
    return;
}

g_registration = result.value();
```

The following source-level changes are intentional:

- The free `erui::register_menu(...)` function is no longer in the API 1.1 C++
  wrapper.
- `ProviderOptions::connect_timeout` was removed. Pass a timeout to
  `erui::connect(timeout)` instead.
- `erui::connect()` without an argument uses a 30-second timeout.
- An API 1.1 connection requests API 1.1 exactly. It reports a host exposing
  only API 1.0 as incompatible instead of silently reducing the feature set.
- `Connection` owns a copied function table. A successful `Registration` also
  keeps the table and provider handle it needs, so the local connection result
  does not have to live for the rest of the process.

Continue to call `connect()` and `register_menu()` from a worker after
`DllMain` returns. Neither operation belongs under the Windows loader lock.

The builder is still declarative and startup-only. Existing 1.0 calls such as
`menu.root()`, `add_toggle`, `add_slider`, `add_button`, choices, submenus,
page presentation, and alerts retain their normal roles. Keep the returned
`Registration` when the mod needs runtime getters, setters, or dialogs.

## Query language from the connection

API 1.0 exposed three convenient language routes:

- the free `erui::query_game_language()` function;
- `menu.game_language()` inside the builder; and
- `Registration::game_language()` after registration.

Those routes are absent from the API 1.1 wrapper. A successful API 1.1
connection means the host's startup language discovery has settled, so query
it once from the connection **before** constructing localized
`ProviderOptions`:

```cpp
const auto connection = erui::connect();
if (!connection) {
    log_error(connection.error().message());
    return;
}

const erui::LanguageInfo language =
    connection.value().game_language();
const Text& text = translations_for(language); // Includes English fallback.

erui::ProviderOptions options{};
options.provider_id = "my-mod";
options.display_name = text.mod_name;
options.owner_module = g_module;

const auto result = connection.value().register_menu(
    options,
    [&](erui::Menu& menu) {
        menu.root().add_button<&show_message>(
            text.button_label, text.button_help);
    });
```

`LanguageInfo::available()` can still be false after a successful connection
if Steam language access is definitively unavailable. Likewise, a non-empty
identifier may map to `GameLanguage::unknown`. Preserve the exact identifier
when useful and always provide an English fallback.

The returned `LanguageInfo` owns its strings. Retain that value or the selected
translation data in your client if callbacks need it later; language is no
longer stored inside `Menu` or `Registration` for you.

This ordering also lets the provider display name be localized without the
separate discovery pass that an API 1.0 client often needed.

## Update the package dependency

For a client built against an installed SDK, change the requested package
version when consuming the 1.1.0 package:

```cmake
# Before: minimum ERNativeUI package release 1.0.0.
find_package(ERNativeUI 1.0.0 CONFIG REQUIRED)

# After: minimum package release 1.1.0, which first ships API 1.1.
find_package(ERNativeUI 1.1.0 CONFIG REQUIRED)
```

These values constrain the downloaded SDK package; they do not select the
runtime function table. The 1.1 headers make `erui::connect()` request ERUI
API 1.1. CMake must also be told where the extracted SDK lives through
`CMAKE_PREFIX_PATH` or `ERNativeUI_DIR`; the
[SDK setup guide](../getting-started/setup.md#option-a-let-cmake-find-the-extracted-sdk)
shows both forms step by step.

The target remains header-only:

```cmake
target_link_libraries(MyMod PRIVATE ERNativeUI::SDK)
target_compile_features(MyMod PRIVATE cxx_std_17)
```

Despite the `target_link_libraries` spelling, `ERNativeUI::SDK` adds headers
and compile requirements, not an import library. The client still discovers
`ERNativeUI.dll` dynamically and can keep its gameplay functionality running
when the host is missing.

Keep the headers and CMake package metadata from one selected SDK release. Test
first with the host packaged in that SDK. At deployment, an API 1.1 client may
use any later compatible 1.x host because same-major hosts retain earlier APIs;
it still cannot use a 1.0 host because negotiation is exact and never silently
downgrades. A future 2.x host is compatible only when its release documentation
explicitly retains API 1.1. Configure every Elden Ring client for Windows x64.

## New API 1.1 capabilities

API 1.1 appends these public feature groups without changing the frozen
API 1.0 prefix:

| Capability | C++ entry point | Purpose |
|---|---|---|
| `text_input` | `Page::add_text_input` | Native editable text plus runtime text get/set operations. |
| `color_picker` | `Page::add_color_picker` | Native RGB color editing plus runtime color get/set operations. |
| `builtin_pages` | `Menu::page(BuiltinPage::...)` | Place ordinary rows in supported built-in Configuration pages. |
| `input_bindings` | `Menu::input_bindings()` | Add provider sections/actions to native controller and keyboard/mouse binding screens. |
| `storage` | `Menu::storage()` | Explicit provider-owned in-memory configuration with opt-in disk load/save. |

The API 1.1 header also supplies a header-only formatter/parser for
`ActionInputs`. That codec can be used with a mod's existing storage backend
without loading the host; applying the decoded assignment at runtime still
requires the Input Bindings capability.

Check capabilities where a feature is declared:

```cpp
const auto result = connection.value().register_menu(
    options,
    [](erui::Menu& menu) {
        if (menu.supports(erui::Capability::text_input)) {
            erui::TextInputOptions input{};
            input.placeholder = L"Enter a name";
            menu.root().add_text_input(
                L"Name", L"Choose the displayed name.", input);
        }
    });
```

The current C++ wrapper accepts API 1.1 only when its complete function table
and all five API 1.1 capability groups are present. These nearby checks are
therefore defensive and make each declaration's dependency obvious; they do
not make a partially implemented API 1.1 host acceptable to this wrapper.

`Connection::supports`, `Menu::supports`, and `Registration::supports` answer
questions at their corresponding lifecycle stage. A capability describes the
negotiated API surface; it does not make private game addresses stable. The
host still validates the running Elden Ring build and fails safely when a
required native boundary cannot be established.

See the [feature matrix](../features.md) for the complete behavior, limits,
and optional GFX presentation of each addition.

## Strict-C clients

No C source change is required for a client that deliberately remains on API
1.0. Keep requesting `ERUI_API_VERSION_1_0` with an output table sized to
`ERUI_API_V1_0_SIZE`.

A C client adopting API 1.1 must perform the same explicit handshake on a
worker thread:

1. Poll for the already-loaded `ERNativeUI.dll` with `GetModuleHandleW` within
   one bounded timeout. Do not link an import library or load a private host.
2. Once the module is present, resolve `ERUI_GetApi` with `GetProcAddress` and
   copy that address into an `ERUI_GetApiFn`.
3. Zero an `ERUI_Api`, then set `size = ERUI_API_V1_1_SIZE`.
4. Call the resolved function as
   `get_api(ERUI_API_VERSION_1_1, &api)`.
5. If it returns `ERUI_HOST_NOT_READY`, wait briefly, reset the complete table,
   restore its size, and retry within a bounded timeout.
6. On `ERUI_OK`, zero an `ERUI_ProviderDesc`, set
   `size = sizeof(ERUI_ProviderDesc)`,
   `api_version = ERUI_API_VERSION_1_1`, and supply `owner_module`,
   `provider_id`, `display_name`, and the desired options. Register it through
   `api.register_provider`, build its rows, and commit it through
   `api.commit_provider`.
7. Call only capability-advertised additions. Treat an unavailable module,
   missing export, timeout, or any other result as a cleanly unavailable UI
   integration.

Request an explicit API version rather than assuming that
`ERUI_API_VERSION_CURRENT` will always mean 1.1 in future SDKs.

## Migration validation checklist

- [ ] Build with the ERNativeUI 1.1.0 SDK as a Windows x64 C++17 client.
- [ ] Remove calls to the free `erui::register_menu` and
  `erui::query_game_language` helpers.
- [ ] Remove `ProviderOptions::connect_timeout`; pass the timeout to
  `erui::connect` if the 30-second default is not desired.
- [ ] Query and retain language/translation data before creating localized
  provider options.
- [ ] Register from a worker after `DllMain`, and handle both connection and
  registration errors without disabling unrelated mod behavior.
- [ ] Keep the provider ID and `owner_module` unchanged and valid.
- [ ] Keep `Registration` if later code needs runtime operations.
- [ ] Gate every adopted API 1.1 feature with its named capability and test its
  documented fallback or failure behavior.
- [ ] Test with the matching 1.1.0 host and a later 1.x host, then test a
  missing host or one exposing only API 1.0;
  the rebuilt client should report the incompatibility without crashing.
- [ ] Verify callbacks, persistence, localization fallback, page navigation,
  and restart behavior in game with Easy Anti-Cheat disabled.
- [ ] Declare ERNativeUI 1.1.0 or any later 1.x release as the runtime
  dependency. Accept a 2.x host only when it explicitly documents retained
  API 1.1 support and the required capabilities; do not ship a private host
  copy with every client mod.

Framework contributors can additionally run the frozen API 1.0 C/C++ clients
under the online [`tests/abi/releases/v1_0`](https://github.com/Flammrock/ERNativeUI/tree/main/tests/abi/releases/v1_0) fixture against the
new host. Those tests protect every client built against API 1.0, including
both already-distributed binaries and new clients intentionally using the 1.0
SDK. Migration is required only when source adopts the API 1.1 wrapper and its
new contract.

For a complete API 1.1 starting point, use the

[first-mod guide](../getting-started/first-mod.md).
